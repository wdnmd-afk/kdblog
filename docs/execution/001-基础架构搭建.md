## 一、目标

搭建一个基于 Next.js 全栈的轻量 CMS，实现以下闭环：

1. 后台统一管理文章、页面、分类、标签四个模块
2. 文章发布时同步完成：SEO 字段校验、正文预渲染为 HTML、版本快照、缓存失效
3. 文章 SEO 元数据全人工维护，带规范提示与强校验
4. 前台仅提供文章详情页 `/posts/{slug}-{id}`，通过 ISR 提供完整 HTML 文档

## 二、技术架构

### 2.1 运行形态

单 Next.js App Router 应用，前台与后台同仓同应用，通过 route group 隔离。

- 框架：Next.js 16.3.5 + React 19.2.8 + TypeScript 5.9
- 样式：Tailwind CSS 4
- 数据库：PostgreSQL（开发期本机安装）
- ORM：Prisma
- 认证：Auth.js v5 Credentials + Argon2
- 校验：Zod（Server Action 入参、SEO 规范共用同一份 schema）
- 编辑器：Tiptap
- 图片处理：sharp
- 后台 UI：Tailwind + shadcn/ui

### 2.3 关键设计决策

#### 决策 1：发布链路全同步单事务

关键词改为全人工维护后，发布不再依赖任何外部服务，因此不引入任务表与后台 worker。

```
publishPost(id)
  ├─ 鉴权（action 内部，不依赖 middleware）
  ├─ seoSchema.parse()          不合规直接返回字段级错误，阻止发布
  ├─ generateHTML(json, sharedExtensions) → sanitize-html 白名单
  ├─ 事务：Post 更新 + SeoMeta upsert + PostRevision 插入 + 裁剪至 20 版
  └─ revalidateTag(`post:${id}`)
```

理由：少一整层运维面（无 Redis、无常驻进程、无轮询），且发布结果对用户是即时确定的。

#### 决策 2：正文预渲染入库 + ISR，而非写静态 HTML 文件

发布时将 Tiptap JSON 渲染并 sanitize 为 `contentHtml` 落库，前台页面直接输出该 HTML 并由 ISR 做全页缓存。

理由：Next 的 ISR 产出本身就是完整 HTML 文档（含完整 `<head>` metadata），SEO 效果与手写 `.html` 文件等价。而真正写文件到磁盘需要自行实现全量重生成、失效队列，且与 Serverless 无持久磁盘、动态能力（预览、浏览量）冲突，本质是重造 ISR。

预渲染入库的额外收益：sanitize 只需在发布这一处执行，XSS 防线单点收敛。

#### 决策 3：URL 采用 `/posts/{slug}-{id}`，以末尾 id 为查询键

- slug 仅作可读装饰，实际查询用 id
- 请求 slug 与当前记录不一致时 301 到正确地址
- `generateMetadata` 始终输出规范 canonical

理由：改标题不会断链，无需维护 slug 唯一约束与历史重定向表。

#### 决策 4：Tiptap extension 列表前后端共享

`lib/tiptap/extensions.ts` 同时被编辑器组件与服务端 `generateHTML` 引用。

理由：一旦两侧分叉，会出现「编辑器内正常、发布后样式丢失」且难以排查。该文件需注释声明禁止单侧修改。

## 三、数据模型

共 9 张表。

| 表 | 关键字段与约束 |
| --- | --- |
| `User` | 单管理员，Argon2 密码哈希 |
| `Post` | 自增 `id`（URL 查询键）、`slug`、`contentJson`、`contentHtml`（`@db.Text`）、`status`、`publishedAt`、`categoryId`、`deletedAt`（软删） |
| `PostRevision` | 全量快照（contentJson + title + excerpt），`version` 递增，**保留最近 20 版**，超出部分在写入同事务内清理 |
| `Page` | 结构同 Post，仅后台管理，不渲染前台 |
| `Category` | `parentId` 自引用成树，查询用 PostgreSQL 递归 CTE |
| `Tag` | name、slug |
| `PostTag` | 文章标签多对多 |
| `SeoMeta` | `targetType + targetId` 复合唯一；`keywords` 使用 PostgreSQL 原生 `String[]` |
| `Media` | 原图路径 + `variants` Json（WebP 与各尺寸路径、宽高） |

### 为什么 SeoMeta 独立成表

1. 页面（Page）同样需要 SEO 字段，独立表可复用
2. 与文章正文解耦，避免并发写互相覆盖

## 四、文章 SEO 字段规范

该规范落地为三处：`lib/seo/schema.ts` 的 Zod 定义（服务端强校验）、编辑器 SEO Tab 的实时提示、以及编辑页内的「填写规范」折叠说明块。

| 字段 | 维护规则 | 校验方式 |
| --- | --- | --- |
| `metaTitle` | 含主关键词且尽量靠前；中文 ≤ 30 字 / 英文 ≤ 60 字符；不堆砌、不重复站名（站名由模板追加） | 实时字数条，超限黄色警告；未含主关键词提示 |
| `metaDescription` | 中文 60–80 字 / 英文 120–160 字符；含主关键词 + 1 个长尾词；说清读者收益，非正文摘抄 | 实时字数条 + 关键词命中提示 |
| `keywords` | 3–8 个，结构为 1 个主关键词 + 2–3 个次要 + 1–3 个长尾；禁止同义词堆砌 | 数量越界阻止保存；自动去重 |
| `slug` | 小写，仅 `a-z0-9-`，≤ 5 个词，含主关键词英文形式；发布后不建议再改 | 格式正则 + 全局唯一校验 |
| `canonicalUrl` | 默认留空（系统按 `/posts/{slug}-{id}` 生成）；仅当同内容也发布于外站时手填 | URL 格式校验 |
| `ogImage` | 1200×630，≤ 200KB；缺省回退正文首图，再回退站点默认图 | 上传时校验尺寸比例 |
| `ogTitle` / `ogDescription` | 留空即继承 `metaTitle` / `metaDescription` | — |
| `robots` | 默认 `index,follow`；草稿与低质页 `noindex,nofollow` | 枚举选择，非自由输入 |
| `structuredData` | 不维护，系统自动生成 Article JSON-LD | 自动 |

### 固定示例

编辑器 SEO Tab 内展示此示例作为填写参考。

```yaml
# 文章标题：Next.js 15 的 ISR 缓存到底怎么按标签精准失效
metaTitle:        "Next.js ISR 缓存精准失效：revalidateTag 实战"
metaDescription:  "讲清 Next.js 15 中 ISR 与 revalidateTag 的配合方式，含发布文章后只刷新单篇缓存的完整代码，避免全站重建。"
keywords:
  - "Next.js ISR"          # 主关键词
  - "revalidateTag"        # 次要
  - "Next.js 缓存失效"      # 次要
  - "增量静态再生成怎么用"   # 长尾
slug:             "nextjs-isr-revalidate-tag"
canonicalUrl:     ""                                  # 留空，系统生成 /posts/nextjs-isr-revalidate-tag-42
ogImage:          "/uploads/2026/02/isr-cover.png"    # 1200x630
ogTitle:          ""                                  # 继承 metaTitle
ogDescription:    ""                                  # 继承 metaDescription
robots:           "index,follow"
```

### SEO 输出回退链

`generateMetadata` 读取 `SeoMeta`，缺失字段按以下顺序回退：

- `metaTitle` → `Post.title`
- `metaDescription` → `Post.excerpt`
- `ogImage` → 正文首图 → 站点默认图

## 六、实施建议

1. **阶段 0.1 不可跳过**。Next 16 的缓存 API 可能已从 `unstable_cache` 迁移到 `"use cache"` 指令，动态 API（`cookies` / `headers` / `draftMode` / `params`）是否必须 await 也直接影响每个文件的写法。以文档为准，不凭记忆。
2. **服务层先于 UI**。所有数据访问收敛到 `server/services/`，禁止在组件内直连 `prisma.post.findMany`，否则软删过滤会漏。
3. **SEO schema 单一事实源**。前端表单校验与后端 action 校验共用 `lib/seo/schema.ts`，不允许各写一份。
4. **sanitize 白名单与 extension 列表联动**。新增 Tiptap 节点必须同步更新白名单，建议补一个单测断言「每个 extension 产出的标签都在白名单内」。
5. 每阶段结束后跑一次 `pnpm lint` 与 `pnpm build`，不积压问题。

## 七、潜在风险分析

| 风险 | 影响 | 缓解措施 |
| --- | --- | --- |
| Next 16 API 与预期不符 | 大范围返工 | 阶段 0.1 强制核实文档；优先使用稳定 API，避免 experimental 项 |
| Tiptap extension 前后端分叉 | 发布后样式丢失，难排查 | 单一共享文件 + 注释声明禁止单侧修改 |
| sanitize 白名单漏配 | 内容节点被静默剥掉 | 单测断言标签覆盖；新增节点走 checklist |
| Server Action 鉴权遗漏 | 未授权写入 | middleware 拦不住直接调用，每个 action 首行必须查 session；code review checklist |
| 软删过滤遗漏 | 回收站文章泄漏到前台 | 所有查询走 services 层；禁止组件直连 Prisma |
| 富文本 XSS | 前台脚本注入 | 发布时服务端 sanitize，白名单模式（非黑名单） |
| 预览 token 泄漏 | 草稿外泄 | HMAC 签名 + 短过期时间；不建表 |
| Page 未来开放前台时 slug 冲突 | 路由撞车 | 建表时即加保留 slug 黑名单校验（posts / admin / api / sitemap.xml / robots.txt 等） |
| PostRevision 存储增长 | 数据库膨胀 | 全量快照但硬限 20 版，写入同事务裁剪 |
| 分类删除语义未定 | 数据孤儿 | 待确认：禁止删除有子分类或有文章的分类，或级联移至「未分类」 |

## 八、优化方案（本期不实施，预留设计空间）

1. **StorageProvider 抽象**：本期仅 local 实现，接口保持 put / delete / getUrl，未来切 S3 / OSS 不动业务代码。
2. **前台扩展**：分类页 / 标签页 / 首页所需的服务层查询在阶段 3 已具备，未来仅需新增路由。
3. **定时发布**：`PostStatus` 预留 `SCHEDULED`，若将来启用需引入 cron 基建（本期无任务基建，故不实施）。
4. **多用户**：`Post.authorId` 字段预留，未来加角色表即可扩展。
5. **全文检索**：PostgreSQL `tsvector` 或外接检索服务，本期后台搜索用 `ILIKE` 足够。

### 功能验收标准

1. 管理员可登录后台，四个模块列表均可访问
2. 新建文章 → 填写正文与 SEO → 发布成功，SEO 不合规时被阻止并提示具体字段
3. 前台 `/posts/{slug}-{id}` 可访问，页面源码含完整 `<head>` metadata 与 Article JSON-LD
4. 访问错误 slug 但正确 id 时 301 到规范地址
5. 编辑已发布文章并再次发布，前台内容更新（缓存按 tag 失效）
6. 版本历史可查看，超过 20 版时最旧记录被清理
7. 草稿通过预览链接可见，未登录直接访问文章页返回 404
8. 软删文章进入回收站，前台不可访问，可恢复
9. 上传图片自动生成 WebP 与三档尺寸
