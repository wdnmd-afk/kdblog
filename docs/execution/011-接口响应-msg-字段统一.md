# 011 接口响应 msg 字段统一

## 一、目标

- 根据用户新增要求，将业务接口中面向用户的提示统一为 `msg`，不再混用 `error`、`message`。
- 同步服务端返回类型、实际响应、前端读取和回归用例，避免只修改返回字段导致提示丢失。
- 延续 010 的友好文案、HTTP 状态码、异常脱敏和字段级校验，不改变既有业务操作。

## 二、范围与协议

本次是在 010 基础上的协议调整：010 为避免兼容风险暂时保留旧字段，用户现已明确要求统一 `msg`，因此同仓生产方和消费方一次迁移，不保留双字段兜底。

| 场景 | 调整后契约 | 保持不变 |
| --- | --- | --- |
| 普通 Server Action 成功 | `{ ok: true, msg: string, data: T }` | `data` 内容和无数据时的 `undefined` |
| 普通 Server Action 失败 | `{ ok: false, msg: string, fieldErrors?: Record<string, string[]> }` | 字段级校验及 `ok` 判别 |
| 批量 Action | `{ ok: boolean, msg: string }` | 部分成功明细和 `ok` 语义 |
| 业务 HTTP 失败 | `{ code: PublicErrorCode, msg: string }` | HTTP 状态与 `Cache-Control: no-store` |
| 图片上传成功 | `{ msg: string, id, url, width, height }` | 现有扁平数据字段，不额外包装 `data` |
| 上传/下载客户端辅助结果 | 成功、失败均使用 `msg`，保留 `ok` 及已有 `data` | 下载成功仅表示已触发浏览器下载 |

- 范围：`server/actions/`、`lib/http-error.ts`、上传/下载辅助模块、图片上传 Route Handler、后台操作和编辑器调用方、上传脚本、错误契约回归脚本。
- 内部 `Error.message`、`PublicError.message`、日志 `message`、Zod `error` / `issues[].message` 和组件局部错误状态不是业务响应字段，不改名。
- Auth.js 自带接口协议、登录查询参数、预览重定向、Markdown 成功文件流和静态资源响应不包装为 JSON。
- 保留用户当前已暂存的 Page 模块删除，不恢复文件，不改数据库、权限、密码、迁移、种子和现有业务数据。

## 三、操作步骤

1. 核对当前工作区、已安装 Next.js 文档、返回类型、HTTP 端点及全部读取 `error` / `message` 的业务调用方。
2. 统一 Action 类型和所有返回分支为 `msg`，成功分支补充与操作语义匹配的中文提示；保留鉴权顺序、事务、缓存失效和表单字段错误。
3. HTTP 错误生成与解析统一读写 `msg`；上传成功补充 `msg`，上传辅助方法校验并传递该字段；下载辅助结果保持文件响应协议不变。
4. 同步后台和编辑器消费者、Markdown 导入的客户端失败对象、上传脚本；复用准确的共享返回类型，不通过旧字段兼容猜测结构。
5. 更新现有错误回归用例，补充仅识别 `msg`、拒绝旧字段、缺失或无效提示安全回退、成功响应提示的覆盖。
6. 静态检查所有生产方与调用方，核对变更范围和差异空白，记录验证结果及未执行项。

## 四、实施建议

- 保持响应现有层级，本轮不引入统一请求库、新 envelope、全局拦截器或额外依赖。
- `msg` 只负责可展示提示，调用方仍根据 `ok` / HTTP 状态和 `code` 判断结果，不按文案分支。
- 保留界面上更具体的成功上下文，例如文章名称、回滚版本号，不因统一字段降低提示质量。
- 对框架 HTML、损坏 JSON、无效字段和不匹配的错误码，继续按 HTTP 状态安全回退；服务端故障仍不透传原始异常。

## 五、潜在风险分析

- 这是旧提示字段的破坏性迁移：站外调用者须改读 `msg`，打开中的旧管理页在更新后需刷新。
- 同步遗漏会导致 Toast 空白或类型不匹配，必须核对普通 Action、批量操作、三个编辑器上传入口及两个导入/导出入口。
- 上传成功不能改成不兼容的嵌套数据；下载成功不能 JSON 化，否则插图或 Markdown 下载会失效。
- 不得把原生异常和日志字段机械替换为 `msg`，否则会破坏错误分类或诊断信息。
- 静态审阅不能替代真实浏览器、类型检查或测试，未经用户明确要求不执行这些命令。

## 六、优化方案

- 以必填 `msg` 的返回类型约束新增分支，批量和行内操作优先复用已确认类型，减少局部重复定义。
- 沿用集中维护的安全文案和 HTTP 解析器，让所有失败入口共享同一规范；不扩大到认证和业务服务重构。
- 通过现有纯函数及模拟 fetch 回归脚本验证协议，不为验证制造数据库故障或写入业务数据。

## 七、验证方式

- 本轮执行：代码审阅、返回结构与类型定义核对、全部调用方和边界分支搜索、`git -c core.safecrlf=false diff --check` 及改动范围检查。
- 回归用例仅更新不执行；用户明确同意后可运行 `pnpm test:errors`，该脚本使用模拟 fetch，不访问实际数据库。
- 未获授权不运行 lint、类型检查、测试、构建、浏览器交互、迁移或 seed。
- 后续人工验收重点：成功和失败响应都有中文 `msg`；错误字段仍就地展示；批量部分成功明细可读；上传和导出故障不会静默失败或下载错误正文。
