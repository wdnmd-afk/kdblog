# 010 接口错误处理与友好提示

## 一、目标

- 区分账号密码错误、登录失效、输入错误、数据冲突、服务不可用、超时和客户端请求失败，避免把数据库连接故障显示为密码错误。
- 提示采用“发生了什么 + 用户下一步能做什么”，不向浏览器泄露数据库地址、SQL、堆栈或原始异常。
- 复用既有表单错误、Toast、Server Action 返回契约，不增加依赖或重做反馈组件。

## 二、范围与现状依据

- 登录：`app/login/page.tsx` 当前把所有 `AuthError` 转为同一句账号密码错误；已核对 Auth.js 的 `type` 和 `cause.err` 定义。
- 写操作：`server/actions/` 的鉴权多在 `try` 外，数据库故障或会话失效直接抛给框架，无法由现有 Toast 展示。
- 统一映射：`server/actions/types.ts` 已有业务错误和四类 Prisma 约束错误映射，缺少连接、超时与服务异常分类。
- 文件接口：上传只捕获鉴权错误且一律返回 401；导出查询在异常处理之外，失败响应也不统一。
- 客户端：图片上传把非 JSON 响应误报成网络错误；Markdown 导出直接点击下载链接，不能检查接口失败；Markdown 解析请求缺少传输失败处理。
- 验证基础：已有 TSX 回归脚本；本次新增不依赖数据库的错误契约回归脚本，但未经用户明确要求不运行。

## 三、错误契约

- Server Actions 保留 `{ ok: false, error, fieldErrors? }`，批量操作保留 `{ ok, message }`，避免破坏既有表单和批量处理。
- 文件 HTTP 接口失败统一为 `{ error: string, code: string }`，并设置 `Cache-Control: no-store`；上传成功结构和 Markdown 下载成功响应头保持不变。
- HTTP 状态：输入错误 400、未登录 401、无权限 403、资源不存在 404、冲突 409、文件过大 413、不支持的文件类型 415、限流 429、未知服务错误 500、服务不可用 503、服务超时 504。
- 错误码和文案集中维护；业务错误保留具体指导，数据库凭据错误不能映射成用户登录失败。
- 登录只在 Auth.js 返回 `CredentialsSignin` 时提示账号或密码错误；服务异常记录原始日志，并输出白名单中的友好提示。

## 四、操作步骤

1. 新增无服务端依赖的错误分类、公开文案及 HTTP 错误响应辅助方法，既有 `normalizeError` 委托统一实现。
2. 调整登录错误映射和无障碍提示，保留成功重定向，不捕获并吞掉 Next.js 的控制流异常。
3. 将现有 Action 的鉴权及输入校验放入既有异常处理范围，确保鉴权仍先于所有校验、读取和写入；保留各业务缓存失效和成功分支。
4. 补齐图片上传和 Markdown 导出的完整异常边界，保留服务端日志，按错误类别返回状态码和安全消息。
5. 客户端上传区分 HTTP 失败、响应格式异常与请求失败；两个导出入口复用先检查响应再下载的流程，并保留编辑器未保存提醒。
6. Markdown 两个导入入口补充请求失败提示，不自动重试、不落库、不清空当前正文。
7. 新增纯错误契约回归脚本，进行静态调用链、返回结构、鉴权顺序及修改范围检查，补充本次执行结果。

## 五、实施建议

- 公共错误工具不能导入 Prisma、文件系统或 Auth.js 运行时代码，避免把服务端依赖带进浏览器包；类型引用使用 `import type`。
- 只使用已核实的业务错误码、Prisma `code` / 初始化异常 `errorCode`、Auth.js `type` / `cause.err`；不从英文报错全文猜测错误类别。
- 原始异常只进入现有服务端日志，禁止把表单密码或令牌作为日志上下文。
- 对未完成移除的 Page 模块，仅同步错误处理，不删除其路由、不修改 Schema 或迁移。

## 六、潜在风险

- 数据库不可用时没有执行到密码验证，不能推断数据库中密码是否正确；必须避免重新 seed 或跳过鉴权。
- 写操作发生网络中断时可能已被服务端执行，不增加自动重试，也不在失败分支清除本地草稿。
- 下载改为 Blob 后要保留 UTF-8 文件名、及时释放对象 URL，并在失败时阻止将错误正文保存成 Markdown。
- 401 与数据库异常必须区分；存储权限异常不能误报为用户无权访问。
- 当前 Page 模型与残留代码不一致属于既有问题，可能影响后续全量类型检查，本次不处理。
- 框架级或浏览器级交互仍需人工回归，静态核对不能替代真实登录、上传和下载验收。

## 七、优化方案

- 本次以统一纯函数和现有反馈入口收敛错误，不引入请求库、全局请求拦截或新的通知系统。
- 后续如需请求追踪编号、全局登录过期跳转或错误统计，单独确认范围后实施，避免本次扩大到权限和监控改造。

## 八、验证方式

- 默认执行：代码审阅、已安装依赖类型定义核对、所有受影响调用方和错误分支检查、Git 改动范围检查。
- 新增回归脚本覆盖错误分类、登录错误映射、HTTP 状态、JSON 错误契约、非 JSON 响应及原始异常脱敏；本轮不运行。
- 需用户明确同意后才执行测试、类型检查、lint 或构建，不停止现有数据库制造故障，不自动登录、不写入业务测试数据。
- 人工验收：密码错误与服务不可用提示不同；登录失效时业务操作出现可读提示；损坏图片、文件过大、导出 401/404/503 均不再误报或静默失败；成功上传、保存、发布和下载行为不变。
