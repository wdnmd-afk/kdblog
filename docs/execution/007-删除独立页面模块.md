## 目标

移除后台「页面」模块及其全部代码与数据库对象。理由是当前版本不产出前台路由，该模块只是占位存储，没有实际作用。

| 数据库 | `pages` 表、`seo_meta.pageId` 列及其唯一索引与外键 |

## 操作步骤

1. 修改 `dashboard.ts`：去掉页面相关类型字段与查询，保留其余统计口径不变。
2. 修改 `admin/page.tsx`：去掉页面 KPI 卡，网格列数改 3。
3. 修改 `trash/page.tsx` 与 `TrashList.tsx`：只处理文章。
4. 修改 `AdminNav.tsx`：去掉导航项。
5. 删除 `app/(admin)/admin/pages/`、`server/services/page.ts`、`server/actions/page.ts`、`getPageSeoMeta`。
6. 修改 `prisma/schema.prisma`：删 `Page` 模型、`User.pages`、`SeoMeta.pageId`，同步注释。
7. 新增迁移 `prisma/migrations/<ts>_drop_pages/migration.sql`：先删 `seo_meta.pageId`（索引 + 列 + 外键），再 `DROP TABLE "pages"`。
8. 重新生成 Prisma Client（`pnpm prisma generate`），否则 `@prisma/client` 仍带 `prisma.page`，步骤 1 的类型改动无法收敛。
9. 更新 `docs/ui-spec.html` 中的路由清单。

## 实施建议

- **迁移顺序不能反**：`seo_meta.pageId` 有指向 `pages` 的外键，先删列再删表。
- 迁移 SQL 手写而非 `prisma migrate dev` 自动生成，避免自动生成器顺带处理无关差异；手写后需用 `prisma migrate status` / `prisma migrate deploy` 对齐。
- 数据库操作涉及数据丢失，执行前必须确认表中内容确实无用（见风险 1）。

## 潜在风险

1. **数据不可恢复**：`DROP TABLE pages` 会连同 `seo_meta` 中通过 `pageId` 关联的 SEO 记录一并消失。执行前需确认现有页面数据无价值。
2. **环境漂移**：本地库、测试库、生产库需分别执行迁移，任一环境漏掉会出现「代码已无 Page、库里表还在」或反过来的情况。代码侧不查询该表，漏删不会导致运行时报错，只会留下垃圾表。
3. **Prisma Client 未重新生成**：`schema.prisma` 改完但未 `prisma generate` 时，类型与运行时仍保留 `prisma.page`，步骤 1 的改动不会通过类型检查——这一步容易被漏掉。
4. **回收站与仪表盘**：两处都合并了页面的数据，改动后需确认文章部分功能不受影响（回收站列表的 `kind` 分派、仪表盘 KPI 布局）。

## 优化方案

- 迁移同时清掉 `pages` 表遗留的索引，避免 PostgreSQL 残留无用索引占用。
- 若将来要恢复页面功能，需要一并恢复：模型、迁移、服务、action、路由，以及保留字校验的调用点（黑名单已保留，无需重新设计）。

## 验证方式

1. 代码审阅：全仓库搜索 `services/page`、`actions/page`、`admin/pages`、`prisma.page`，确认无残留引用。
2. 类型与构建：`pnpm build`（需用户确认后执行），确认删除后无残留 import。
3. 数据库：迁移后连接数据库确认 `pages` 表与 `seo_meta.pageId` 列已不存在。
4. 手工回归：仪表盘三张 KPI 卡正常、回收站文章的还原与彻底删除正常、后台侧栏无「页面」项。
