# 009 后台数据库连接恢复

## 一、目标

恢复 `/admin` 依赖的本机 PostgreSQL，不通过跳过鉴权或吞掉异常掩盖数据库连接故障。

## 二、范围与定位依据

- 调用链：后台布局 → `lib/auth.ts` 的 `getVerifiedAdmin()` → `lib/db.ts` 的 Prisma adapter → `DATABASE_URL`。
- 当前目标为 `127.0.0.1:5432/kdblog`，与 `docs/本地开发环境.md` 一致；不记录连接凭据。
- Next.js 仍监听 16673，但 5432 未监听，指定数据目录的 `pg_ctl status` 返回 `no server running`。
- 现有实例为 PostgreSQL 16，程序位于 `E:\pg16\pgsql\bin`，数据目录为 `E:\pg16data`，未注册服务，不会开机自启。
- 2026-09-24 的最后一段数据库日志显示进程异常终止后数据库关闭；不能据此断定本次停机由机器重启导致。
- 登录、仪表盘、受保护的 Server Action 与 Route Handler 均依赖数据库，修改单个用户查询不能恢复这些调用。
- 本次只启动现有实例并补充本地操作文档；不修改业务代码、环境变量、表结构、业务数据或用户既有改动。

## 三、操作步骤

1. 预读项目规则、依赖、路由、认证接口、状态、工具与组件模块、Prisma 配置及本地环境文档；核对当前 Next.js 的错误处理与环境变量规则。
2. 核对连接目标、进程、端口、数据目录版本和日志，确认实例停止且端口未被其他实例占用。
3. 用 `Start-Process -WindowStyle Hidden -PassThru` 运行 `E:\pg16\pgsql\bin\pg_ctl.exe`，参数为 `-D E:\pg16data -l E:\pg16data\server.log -w -t 60 start`；对返回的进程对象调用 `WaitForExit()`，只等待启动器结束，再检查退出码。
4. 查看启动结果、运行状态、监听地址及最新日志；若失败，保留现场继续定位，不删除 PID、WAL 或数据目录，不初始化新库。
5. 在本地环境文档补充 PowerShell 启动方式和此类 `/admin` 报错的处理入口。
6. 静态核对文档差异及改动范围，由用户刷新已登录的 `/admin` 页面确认页面级恢复。

## 四、实施建议

- 保留 `getVerifiedAdmin()` 的数据库回查：有效 JWT 不代表对应用户仍存在，跳过回查会破坏认证约束。
- 使用 PostgreSQL 16 的绝对路径，避免误用 PATH 中 Scoop 安装的另一版本打开现有数据目录。
- 先恢复数据库，不重启正在运行的 Next.js；若刷新后仍报错，再依据新日志判断。

## 五、潜在风险

- 异常退出可能触发 PostgreSQL 自动恢复，必须等待启动结果；恢复失败时不得重建或重置数据。
- 本次不注册系统服务，下次重启后仍需手动启动。
- 本机 trust 认证仅适合开发，不额外开放监听地址或防火墙端口，不将此配置用于生产。
- 服务接受连接不代表登录态页面和全部业务功能均已验证。

## 六、优化方案

- 补齐手动操作文档，不把本机固定路径写进跨平台 `pnpm dev`。
- 如需开机自启，后续单独确认 Windows 服务账号、目录权限和启动策略，本次不实施。

## 七、验证方式

- 核对代码调用链、配置、数据库版本和修改范围。
- 查看服务启动退出码、运行状态、端口监听与数据库自身日志，确认运行环境恢复情况。
- 不执行 lint、类型检查、自动化测试、构建、迁移或 seed，不运行写入业务数据的验证脚本。
- 不自动登录或发起页面请求，最终说明页面级行为仍待用户刷新确认。
